## Run it

    cp .env.example .env     # optional: every setting has a safe default
    deno task dev            # API on http://localhost:8000, docs on http://localhost:8000/docs
    deno task test           # all tests (no server, no port needed)
    deno task check          # type-check src/, tests/, scripts/
    deno fmt --check && deno lint

Only Deno is needed: no Node.js and no `npm install`. Deno downloads the packages listed
in `deno.json`. Deno KV and `Deno.cron` are unstable APIs, so `deno.json` turns them on
(`"unstable": ["kv", "cron"]`) and the run tasks also pass
`--unstable-kv --unstable-cron`.

## Design decisions (R8)

**Tables.** `users` (id, email unique, password_hash, role, created_at), `sessions`
(token, user_id, expires_at; given) and `tasks`:

| Column       | Type                                          | Notes                                                  |
| ------------ | --------------------------------------------- | ------------------------------------------------------ |
| id           | integer PK autoincrement                      |                                                        |
| user_id      | integer NOT NULL → users.id                   | the owner                                              |
| title        | text NOT NULL                                 | 1 to 100 characters (Zod)                              |
| status       | text NOT NULL DEFAULT 'todo'                  | `todo`, `in-progress`, `done`                          |
| priority     | text NOT NULL DEFAULT 'medium'                | `low`, `medium`, `high`                                |
| created_at   | integer NOT NULL DEFAULT strftime('%s','now') | a SQL default, so every row gets its own time          |
| due_date     | text NULL                                     | my own field, `YYYY-MM-DD` (second migration, Bonus 1) |
| deleted_at   | integer NULL                                  | soft delete (Bonus 2)                                  |
| attachment   | text NULL                                     | generated file name of an image (Bonus 12)             |
| completed_at | integer NULL                                  | when it became done (Bonus 14)                         |

Index: `idx_tasks_user_status (user_id, status)` (Bonus 4). Times are Unix seconds, the
same as the given `users.created_at`.

`schema.ts` and the SQL always agree because the SQL is generated from `schema.ts` by
Drizzle Kit (Bonus 1), and `tests/schema_test.ts` compares the columns of each Drizzle
table with `pragma_table_info` of the real database.

**Routes.**

| GET /health, /healthz                             | no       | 200                                 |                         |

| POST /auth/register                               | no       | 201 `{ id, email, role }`           | 400, 409                |
| POST /auth/login                                  | no       | 200 `{ token }`                     | 400, 401, 429           |
| POST /auth/logout                                 | yes      | 200 `{ ok, revoked }`               | 401                     |
| GET /api/tasks?page&limit&status&priority&deleted | yes      | 200 `{ items, page, limit, total }` | 400, 401                |
| POST /api/tasks                                   | yes      | 201 task                            | 400, 401                |
| GET /api/tasks/:id                                | yes      | 200 task                            | 400, 401, 404           |
| PUT /api/tasks/:id                                | yes      | 200 task                            | 400, 401, 404           |
| DELETE /api/tasks/:id                             | yes      | 200 `{ ok: true }`                  | 400, 401, 404           |
| POST /api/tasks/:id/restore                       | yes      | 200 task                            | 400, 401, 404           |

| GET /openapi.json, /docs                          | no       | 200                                 |                         |

**Why these decisions.**

- _Another user's task is 404, not 403._ A 403 would say "this id exists, but it is not
  yours", so a user could find out which ids exist. Every query in `tasks_repo.ts` has the
  owner in its `WHERE` (`own()` and `alive()`), so another user's row is simply not found.
- _The user id comes only from the token._ `requireAuth` stores it in the context; no
  route reads a user id from the body or the URL.
- _No SQL is built from strings._ Every query uses Drizzle operators (`eq`, `and`,
  `isNull`) or `?` placeholders, so user input is always a parameter (SQL injection
  defence).
- _One error shape:_ `{ error, issues?, requestId }`. Validation errors list each field in
  `issues`; every failure (400, 401, 403, 404, 409, 413, 415, 429, 500, 503, unknown
  route, bad token) goes through `fail()` in `errors.ts`. The `requestId` is the same as
  the `x-request-id` header and the log line, so a client can quote it.
- _The `:id` is validated too._ `/api/tasks/abc` is a 400 with the error shape, not a
  crash and not a silent 404.
- _PUT replaces the task._ POST and PUT share one body schema with defaults, so a PUT that
  leaves out `priority` sets it back to `medium`, and one without `dueDate` clears it.
  This is what "replace" means; a partial change would be a PATCH.
- _Login does not reveal which emails exist._ A wrong email and a wrong password give the
  same 401 message, and for an unknown email the password is still compared with a dummy
  bcrypt hash, so both cases take about the same time.
- _Emails are trimmed and lower-cased_ by the Zod schema, so `AYSE@example.com` and
  `ayse@example.com` are one account (a test checks the 409).
- _Tokens are JWTs by default_ (Bonus 7), but `AUTH_MODE=session` switches back to the
  given sessions table without changing a route. Both are behind one `TokenService`
  interface.
- _A fresh database per test._ `tests/helpers.ts` gives every test its own temporary
  SQLite file (`freshApp()` / `freshEnv()`), so tests never share data and can run in any
  order.

## My own log (R8)

These entries were written by the AI assistant (see the note at the top). Each experiment
was run on 23 November 2026 against this repository: the code was broken on purpose, the
real output was copied below, and the change was reverted afterwards (`git checkout .`,
plus `git clean -fd drizzle` for entry 5). Request ids are from those runs.

### 1. POST a task without the content-type header

- **Tried:** sent valid JSON with curl `-d` but no `content-type` header:
  `curl -s -i -X POST localhost:8000/api/tasks -H "Authorization: Bearer $TOKEN" -d '{"title":"no header"}'`
- **Observed:**

      HTTP/1.1 415 Unsupported Media Type
      {"error":"send the body as JSON with content-type: application/json","requestId":"106c8cfe-7ff9-4277-bcb8-7a6779b57ca6"}

- **What it showed:** the JSON itself was fine, but curl `-d` labels the body
  `application/x-www-form-urlencoded`. The request was rejected before Zod ever ran, and
  `app.onError` still turned it into the usual `{ error, requestId }` shape.
- **Learned / changed:** adding `-H 'content-type: application/json'` to the same request
  gave `HTTP/1.1 201 Created`. Every JSON curl example in this README sends that header.

### 2. Remove the owner check from `own()` in `src/tasks_repo.ts`

- **Tried:** changed `and(eq(tasks.id, id), eq(tasks.userId, userId))` to
  `and(eq(tasks.id, id))` and ran `deno task test`.
- **Observed:** the code still type-checked and the server would still run, but 4 tests
  failed (`FAILED | 68 passed | 4 failed`), for example:

      user B cannot read, change or delete user A's task (404 each) => ./tests/tasks_test.ts:85:6
      error: AssertionError: Values are not equal.
          [
      -     200,
      -     200,
      -     200,
      +     404,
      +     404,
      +     404,
          ]

  The other three were `another user never gets my cached task` (200 instead of 404),
  `another user cannot restore my deleted task` (200 instead of 404) and
  `only the owner can upload or download` (201, 200 instead of 404, 404).
- **What it showed:** with one `eq` missing, user B could read, change and delete user A's
  task. Nothing crashed; only the tests noticed.
- **Learned / changed:** the owner condition lives in one helper (`own`) that every query
  uses, and the cross-user tests stay in the suite because they are the only thing that
  catches this kind of bug.

### 3. Start in production with the default or a short `JWT_SECRET`

- **Tried:** `APP_ENV=production deno run -A src/main.ts`, then the same with
  `JWT_SECRET=abc`, then with `JWT_SECRET=$(openssl rand -hex 32)`.
- **Observed:** the first two stopped before the server opened (exit code 1):

      Invalid configuration:
        JWT_SECRET: the default secret is not allowed in production

      Invalid configuration:
        JWT_SECRET: use at least 32 characters in production

  The random 64-character secret started normally:
  `Listening on http://0.0.0.0:8000/ (http://localhost:8000/)`.
- **What it showed:** the check happens once, in `src/config.ts`, at startup, so a
  misconfigured deployment cannot serve a single request with a guessable secret.
- **Learned / changed:** `.env.production` deliberately holds no secret; the real
  `JWT_SECRET` must come from the environment, and the default is only for local
  development and tests.

### 4. Tamper with a JWT, then log out and reuse it (JWT mode vs session mode)

- **Tried:** changed one character in the middle of the token's signature and called
  `GET /api/tasks`; then called `POST /auth/logout` with the real token and reused it.
- **Observed (JWT mode, the default):**

      HTTP/1.1 401 Unauthorized
      {"error":"unauthorized","requestId":"b68f73e0-cca6-4148-8387-c2ef2ba1a45f"}

  Logout answered `{"ok":true,"revoked":false}` and the same token then still got `200`.
- **Observed (`AUTH_MODE=session deno task dev`):** the token was a 36-character session
  id; before logout `200`, logout answered `{"ok":true,"revoked":true}`, and afterwards:

      HTTP/1.1 401 Unauthorized
      {"error":"unauthorized","requestId":"233a1108-2e93-4173-a2ce-98ecf2154dc5"}

- **What it showed:** a changed signature is always rejected, but a valid JWT cannot be
  revoked by logout: it is not stored anywhere and stays valid until it expires (1 hour).
  A session row in the database can be deleted, so session logout really ends access.
- **Learned / changed:** this is why the app supports both modes and why logout reports
  `revoked` honestly instead of pretending the JWT was cancelled.

### 5. Add a column to `schema.ts` without generating a migration

- **Tried:** added `notes: text("notes"),` under `completedAt` in the `tasks` table and
  ran `deno task test` without running `db:generate`.
- **Observed (first surprise):** the type-checker stopped the run before any test, because
  the `Task` fixture in `tests/cache_test.ts` had no `notes` field:

      TS2741 [ERROR]: Property 'notes' is missing in type '{ id: number; userId: number; title: string; status: "todo"; ... completedAt: null; }' but required in type '{ ... notes: string | null; }'.
          at file:///workspace/mis233/out/assignment5/tests/cache_test.ts:7:68
      error: Type checking failed.

- **Observed (database):** running the tests with `--no-check` to reach the database gave
  `FAILED | 39 passed | 33 failed`, with errors such as
  `LibsqlError: SQLITE_ERROR: table tasks has no column named notes` (inserts) and
  `LibsqlError: SQLITE_ERROR: no such column: notes` (selects).
- **Fix:** `deno task db:generate --name add_notes` wrote `drizzle/0007_add_notes.sql`
  containing ``ALTER TABLE `tasks` ADD `notes` text;``. After that the `--no-check` run

- **Learned / changed:** `schema.ts` is what TypeScript knows and the migration is what

### Bonus 4: Indexes and EXPLAIN

The index is in `schema.ts` and in the migration `0003_index_user_status.sql`:

```sql
CREATE INDEX `idx_tasks_user_status` ON `tasks` (`user_id`,`status`);
```

`deno task explain` makes a database with 20,000 tasks for 20 users (inserted in batches
of 500), drops the index, measures, creates it and measures again (average of 200 runs):

```text
rows in tasks: 20000
before rows : SCAN tasks
before rows : 2.650 ms per query
before total: SCAN tasks
before total: 0.485 ms per query
after  rows : SEARCH tasks USING INDEX idx_tasks_user_status (user_id=? AND status=?)
after  rows : 2.380 ms per query
after  total: SEARCH tasks USING COVERING INDEX idx_tasks_user_status (user_id=? AND status=?)
after  total: 0.033 ms per query
```

`rows` is `SELECT * FROM tasks WHERE user_id = ? AND status = ?` and `total` is the same
with `count(*)`, which the pagination also runs. Without the index SQLite reads all 20,000
rows (`SCAN`); with it, it jumps to the matching ones (`SEARCH ... USING INDEX`). The
count became about 15 times faster because the index alone answers it (`COVERING INDEX`).
The `SELECT *` gained less, because each call still returns about 333 full rows and
building them costs more than finding them. What an index costs: every insert, update and
delete must also update the index, and it takes disk space, so index only the columns that
queries filter on. `summary_test.ts` checks that the plan uses the index.

### Bonus 6: A connection pool (Postgres or SQLite)

**Option B: my own pool on SQLite.** `src/pool.ts` is a generic `Pool<T>`: `acquire()`
gives an idle item or waits in a FIFO queue, `release()` hands the item straight to the
next waiter, and `use(fn)` always gives it back in a `finally`. `createDb()` opens
`DB_POOL_SIZE` (default 4) libSQL clients on the same file, plus one main connection for
start-up, jobs and scripts. `migrate()` sets `PRAGMA journal_mode=WAL` (stored in the
file) and `PRAGMA busy_timeout=5000` on every connection. The middleware `withConnection`
in `db.ts` runs on every `/api/*` request: the request borrows one connection
(`c.get("conn")`), all task, summary and admin queries use it, and it is given back when
the response is done, even after an error.

Tests (`pool_test.ts`): 20 concurrent jobs on a pool of 3 never run more than 3 at once
and all 20 finish; an item comes back even when the job throws; after 10 parallel requests
plus a 404 and a 400 every connection is idle again; the database is in WAL mode.

- _Pool size 4:_ a small multiple of the CPU cores is enough for one SQLite file; more
  connections would only wait for the same write lock.
- _When all are busy,_ a request waits in the queue until one is released (no error). With
  `busy_timeout` a connection that meets a locked file waits up to 5 s instead of failing
  with `SQLITE_BUSY`.
- _Why SQLite gains little:_ SQLite lives in the same process and allows one writer at a
  time, and the local libSQL driver runs each statement synchronously. A pool mainly gives
  each request its own connection (so a transaction on one connection cannot mix with
  another request) and lets WAL readers work next to the writer. With Postgres a pool
  matters much more, because opening a network connection is slow and the server runs
  queries in parallel. The same pool also works for a remote libSQL database (Turso, Bonus
  19).

### Bonus 7: JWT instead of sessions

`src/auth.ts` has `signToken(userId, role, secret)` (HS256, the user id in `sub`, the role
in a `role` claim, expires after one hour) and `verifyToken(token, secret)`, which returns
`null` for a bad, tampered or expired token and accepts only HS256. Login answers with a
JWT and `requireAuth` verifies it without a database lookup. The secret comes from
`JWT_SECRET` through the config; production refuses the default `dev-secret` (and anything
shorter than 32 characters). The given sessions still work: `AUTH_MODE=session` swaps the
`TokenService`, and the routes and tests stay the same.

Tests (`jwt_test.ts`): the token has three parts, `sub` "1", role "user" and `exp - iat` =
3600; a tampered token (one character of the signature changed), an expired token and a
token signed with another secret are all 401; and the two designs side by side on logout.

|                    | Sessions table                                                     | JWT                                                               |
| ------------------ | ------------------------------------------------------------------ | ----------------------------------------------------------------- |
| Checking a request | one database lookup                                                | only a signature check, no lookup                                 |
| Several servers    | all need the same database                                         | any server with the secret can check it                           |
| Logout / revoke    | delete the row: the token dies at once (`revoked: true`, then 401) | impossible before `exp` (`revoked: false`, the token still works) |
| Role change        | seen at once                                                       | seen only after the next login (the role is in the token)         |
| Stolen token       | can be deleted                                                     | valid until it expires, so keep the lifetime short                |

### Bonus 15: Rate limit on login

`src/rate_limit.ts` keeps a `Map` from email to `{ n, resetAt }`. A failed login counts;
before the password is checked, 5 or more failures inside the one-minute window answer 429
with a `Retry-After` header (seconds left). A successful login clears the counter, and an
old window starts again from 1. The clock is injectable, so the test can move time
forward. See the curl section: five 401s, then 429 with `retry-after: 60` even with the
right password. Tests (`rate_limit_test.ts`): five failures then 429 with Retry-After even
when the password is right, another email is not affected, after the window it works
again, and a success clears the count.

What it does not protect against: the counter lives in one process, so with several
servers each has its own count (an attacker gets 5 tries per server), and a restart
forgets it (Deno KV or Redis would fix both). It is per email, so one attacker trying one
common password on many emails is never blocked (that needs a limit per IP address too).
And an attacker can lock a real user out for a minute on purpose by failing 5 times with
their email.

### Bonus 16: A cache with Deno KV

`main.ts` opens KV once (`Deno.openKv(KV_PATH)`), with `--unstable-kv`. `src/cache.ts`
caches `GET /api/tasks/:id` under `["task", userId, id]` for 60 seconds
(`expireIn: 60_000`): a hit returns the stored task, a miss loads it from the database and
stores it. The user id in the key means one user can never be served another user's cached
task (and the loader still checks the owner on every miss). Update, delete, restore and
upload call `kv.delete(key)`, so a changed task is never served stale. The response has an
`x-cache: hit|miss` header; see the curl section (miss, then hit). Tests (`cache_test.ts`,
on an in-memory KV): the second read is a hit and the database was read once (a counting
loader and `dbReads`); the key contains the user id and another user gets a miss; after a
PUT the next read is a miss with the new title, and after a DELETE it is 404; user B never
gets user A's cached task.
